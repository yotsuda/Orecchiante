[HANDOFF.md](HANDOFF.md) を読む。** ここ（ゴール・原則・作業の順番）はめったに変えない。

## 1. 長期ゴール

**録音（mp3 / wav）を、ローカルだけで、数秒〜十数秒で、直せる `.lys` に書き起こす。**

- 最初の製品はコード譜。テンポ・拍子・調・小節線・各小節のコードを読み、自信のない箇所に
  `@todo` を付ける。横に置くファイルが各小節の時刻を持ち、エディタは直しながら原音のその小節を鳴らせる。
- クラウドの AI は使わない。小さなローカルモデルと、音楽の規則による組み立ての組み合わせ。
- Lily# には同梱しない。独立したプログラムとして `.lys` を書き、`lysc` で確かめる（Calamo と同じ立ち位置）。
- 旋律・ベース・ドラムの採譜はコード譜の後。やるかどうかも含めて M5 で決める。

## 2. 設計の原則

これまでの作業で確かめたこと。変えるときは理由を HANDOFF に書く。

1. **正解は Lily# に作らせる。** 生成した `.lys` を `lysc wav` で鳴らし、コード行を正解にする。
   LilyPond は使わない。`python` は PATH 上の LilyPond のものを拾うので、`py -3.12` か `.venv` を使う。
2. **音の聞き分けは学習し、組み立ては規則で書く。** モデルは「この半拍で何が鳴っているか」だけを答える。
   小節線・コードが変われる場所・拍子・調は規則。モデルが自信を持てないときは規則側に任せる。
3. **数字は必ず全セットで測り直す。** 変更のたびに全セットを測り、README の表を実測値に差し替える。
   推測で数字を書かない。書き出した `.lys` は全部 `lysc check` に通す。
4. **どのセットを見て決めたかを書く。** 値を選ぶのは学習用（seed100）と `scratch/alt-*`。
   テスト用のセットを見て決めた場合は、そう書く。本当に見ていないセットが要るときは新しい seed を作る。
5. **捨てた案を記録する。** 効かなかった案は HANDOFF の「捨てた案」に 1 行で残し、同じ案を試し直さない。
6. **合成曲の数字を実録音の精度と言わない。** 報告は結論から書き、確かめたことと確かめていないことを分ける。
7. **録音・モデル・SoundFont は commit しない。** 作り直すコマンドを README に書く。
8. **push はしない。** push はユーザーが行う。commit まで行い、必要なコマンドを伝える。

### B. 実録音で学習したモデルを耳にする（M2）

2026-11-14 に方針を変えた（ユーザー了承）。**耳（拍・小節頭・コードの聞き分け）は、実録音で学習された
公開のローカルモデルを土台にする。Dettato が作るのは、それを直せる譜面に組み立てる側**（小節に揃える、
印を付ける、繰り返しをまとめる、`.lys` に書く）。自作の拍追跡と、合成曲だけで学習したクロマのモデルは、
合成曲用の比較対象として残すが、これ以上は磨かない。原則 2 の「聞き分けは学習、組み立ては規則」は変わらない。

- **B0 上限を測る（完了、2026-11-14）。** RWC-P 100 曲で、Beat This! の小節線＋BTC のコードが、規則なしの素の出力で
  小節線 F 93.8%・ルート 82.6%・長短 77.4%（自作: 66.1%・74.7%・63.4%）。正しい小節線を与えても自作のコードは
  77.3%・66.2% にしかならない。数字は README。
- **B1 読み取り器の耳を差し替える（完了、2026-11-14）。** `read_chords.py --ears`。`rwc-dev` でルート 84.8%・長短 79.1%・
  小節線 93.3%、`rwc-test` で 86.4%・81.3%・94.4%。合成曲はコードが同等、小節線は Beat This! の分だけ負ける（HANDOFF）。
  当初の項目: `read_chords.py` が (a) Beat This! の拍と小節頭、(b) 実録音のコードモデルの
  フレームごとの確率、を受け取り、今の探索（コードは小節線で変わりやすい・小節の途中は高くつく）で組み立てる。
  拍子は拍の番号と拍の中の刻みから決める（いまは 6/8 が 2 拍子に、合成曲でテンポ・拍子が 17〜20/24 に落ちる）。
  `.lys` と `.dettato.json` を書き、`lysc check` に通す。
  終わり: `rwc-dev` で B0 の素の数字（ルート 81.9%・長短 76.3%・小節線 93.3%）以上。合成曲の全セットで今の読み取り器と
  同等以上、または落ちる理由の記録。使うときのモデルは Beat This! の `final0`（RWC を学習済みなので、測るときは fold のモデル）。
- **B2 印の質（完了、2026-11-14。目標には届かず、理由と届く所を記録）。** `rwc-test` で印 23.2%・誤りの 64.2%
  （30% に付ければ 74.0%、8 割には 38%）。確率からは指せない誤りが残る。M2 の印の目安の扱いは §5。
  当初の項目: コードモデルの確率から確信度を作り、`rwc-dev` で較正する。
  終わり: `rwc-test` で「印 3 割以下・ルートか長短の誤りの 8 割を拾う」か、それが無理な理由。
- **B3 コードモデルを決める（完了、2026-11-14）。** crema 0.2.0（BSD 2-Clause。重みもライセンスの内と作者が明言、
  6.4 MB、ONNX にできる）。`rwc-test` でルート 87.1%・長短 82.0%（BTC 86.4%・81.3%）。BTC は重みの扱いが不明のまま
  なので配らない。BTC を 2 つ目の耳にすると 88.5%・83.6% で印も良くなるが、作者の明言待ち（§5）。
  当初の項目: BTC のまま使うか、別の公開モデルか、自前で学習するか。見るもの: 重みのライセンスと
  学習データの素性（BTC は市販曲で学習。重みは MIT のリポジトリに同梱だが、重みについての明記はない）、精度、
  大きさと速さ、ONNX にできるか（D2）。自前で学習する場合のデータは §5 の判断待ち。
  終わり: 配るものに入れるモデルが決まり、理由が HANDOFF にある。

## 4. セッションの進め方

### 始めるとき

1. この ROADMAP と HANDOFF を読む。
2. HANDOFF の「環境」どおりに動くことを 1 コマンドで確かめる（全セットの測定が前回の数字と一致する）。
3. HANDOFF の「次の一手」から始める。別のことを始めるなら、理由を先に言う。

### 終えるとき（義務）

1. 全セットを測り直し、README の表を合わせる。書き出した `.lys` を `lysc check` に通す。
2. commit する（push はしない）。
3. **HANDOFF を書き換える。** 追記ではなく書き換え。200 行を超えさせない。経緯は git の履歴に任せ、
   HANDOFF には現在地・次の一手・捨てた案・未決の判断だけを残す。
4. ユーザーへの報告は結論から。数字は前回 → 今回で示し、確かめていないことを分けて書く。
5. **次をどちらで進めるのが有利かを、必ず報告の最後に書く。** 形式は次のとおり。

   > **次の進め方: 同じセッションで続ける / 新しい会話で始める**
   > 理由: （1〜3 点）
   > 新しい会話で始める場合に最初に読むもの: （ファイル名）

   判断の目安:

   | 同じセッションで続ける方が有利 | 新しい会話で始める方が有利 |
   |---|---|
   | 次の一手が、いま頭にある細部（調査中の曲、試した値、まだ書いていない所見）を直接使う | 項目の「終わり」を満たして commit し、HANDOFF が最新になった |
   | 途中の実験や未 commit の変更が残っている | 次の一手が別の作業の流れ（A → B など）に移る |
   | 会話がまだ短く、要約（コンテキストの圧縮）が起きていない | 会話の要約がすでに起きた。細部は失われているので、続ける利点が小さい |
   | 原因の切り分けの途中で、仮説がまだ絞れていない | 長いログや捨てた仮説が会話に溜まり、次の判断を引きずりそう |

   迷ったら「新しい会話」を勧める。そのために HANDOFF を、読めば続きができる状態にしておく。
   「同じセッションで続ける」を勧めるときも HANDOFF は書き換える（会話は予告なく要約されるため）。

## 5. ユーザーに決めてもらうこと

- **実録音。** 測るのは RWC-P 100 曲で足りた。ユーザーが使いたい種類の曲（弾き語り、ライブ録音など）が
  RWC-P と違うなら、コードの分かっている曲を数曲もらえると、その種類での数字が出せる。
- **RWC を学習に使うか。** RWC は CC BY-NC 4.0。測るだけなら問題ないが、学習に使ったモデルを配るなら
  非営利の条件がモデルに及ぶかを決める必要がある。決まるまで学習には使わない（合成曲と、条件の緩いデータだけ）。
- **M2 の印の目安。** 「誤りの 8 割に印、印は 3 割以下」は `rwc-test` で届かなかった（B2）。繰り返しの照合（C2）も
  印には効かなかった。2 つ目の耳（BTC、0.4.0）で近づいた（数字は HANDOFF）。下げるか、印を増やすかは HANDOFF の「未決」。
- **和音のないイントロ・旋律だけの弱起を譜面に書くか。** いまは最初の和音の小節から書く（C1）。書くなら N.C. の小節として。
- **section の書き方。** 細切れが読みにくければ、まとめる条件を緩めるか、書かない指定を足す（HANDOFF の「未決」）。
- **決まったこと（2026-11-14）:** 他者が学習した公開モデルを組み込んでよい（ライセンスが配布を許すものに限る）。
- **決まったこと（2026-11-16）: BTC を 2 つ目の耳にする**（オーナー決定。0.4.0）。リポジトリの MIT のもとで、表示を付けて同梱する。
  作者には尋ねない（12 件の issue に返事は 2020 年の 1 件だけ、ほかのアプリも組み込んで公開している）。重みについて作者が何も言っていない曖昧さは残る。
- **決まったこと（2026-11-14）:** 配る形（D2）は VS Code 拡張に入れる .NET の実行ファイル。
  拡張は Lily# とは別（`yotsuda.dettato`。Calamo の `yotsuda.calamo` と同じ形）。
- **決まったこと（2026-11-14）:** 録音を `.lys` に変換するメニューは Lily# 本体が持つ。Dettato の拡張は読み取り器を運び、
  場所と版を返すだけにする。理由: 変換の後の作業（プレビュー、`@todo` の表示、小節の原音を鳴らす）がすべて Lily# のもの。
  Calamo の「Convert Image/PDF to Lily# (.lys)…」と並ぶ。Lily# なしでは `.lys` は描けず鳴らせないので、単独で動く利点がない。
  代償は、メニューを変えるたびに Lily# のリリースが要ることと、両者の約束を決める必要があること（D3）。移す順は §3 の D3・D4。
