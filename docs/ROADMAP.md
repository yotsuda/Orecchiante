# Dettato ロードマップ

複数のセッションにまたがる作業の方向づけ。**毎セッションの最初に、これと
[HANDOFF.md](HANDOFF.md) を読む。** ここ（ゴール・原則・作業の順番）はめったに変えない。
HANDOFF（現在地と次の一手）は毎セッションの終わりに書き換える。

作成: 2026-11-14。

## 1. 長期ゴール

**録音（mp3 / wav）を、ローカルだけで、数秒〜十数秒で、直せる `.lys` に書き起こす。**

- 最初の製品はコード譜。テンポ・拍子・調・小節線・各小節のコードを読み、自信のない箇所に
  `@todo` を付ける。横に置くファイルが各小節の時刻を持ち、エディタは直しながら原音のその小節を鳴らせる。
- クラウドの AI は使わない。小さなローカルモデルと、音楽の規則による組み立ての組み合わせ。
- Lily# には同梱しない。独立したプログラムとして `.lys` を書き、`lysc` で確かめる（Calamo と同じ立ち位置）。
- 旋律・ベース・ドラムの採譜はコード譜の後。やるかどうかも含めて M5 で決める。

## 2. 設計の原則

これまでの作業で確かめたこと。変えるときは理由を HANDOFF に書く。

1. **正解は Lily# に作らせる。** 生成した `.lys` を `lysc wav` で鳴らし、コード行を正解にする。
   LilyPond は使わない。`python` は PATH 上の LilyPond のものを拾うので、`py -3.12` か `.venv` を使う。
2. **音の聞き分けは学習し、組み立ては規則で書く。** モデルは「この半拍で何が鳴っているか」だけを答える。
   小節線・コードが変われる場所・拍子・調は規則。モデルが自信を持てないときは規則側に任せる。
3. **数字は必ず全セットで測り直す。** 変更のたびに全セットを測り、README の表を実測値に差し替える。
   推測で数字を書かない。書き出した `.lys` は全部 `lysc check` に通す。
4. **どのセットを見て決めたかを書く。** 値を選ぶのは学習用（seed100）と `scratch/alt-*`。
   テスト用のセットを見て決めた場合は、そう書く。本当に見ていないセットが要るときは新しい seed を作る。
5. **捨てた案を記録する。** 効かなかった案は HANDOFF の「捨てた案」に 1 行で残し、同じ案を試し直さない。
6. **合成曲の数字を実録音の精度と言わない。** 報告は結論から書き、確かめたことと確かめていないことを分ける。
7. **録音・モデル・SoundFont は commit しない。** 作り直すコマンドを README に書く。
8. **push はしない。** push はユーザーが行う。commit まで行い、必要なコマンドを伝える。

## 3. 作業の順番

1 項目がおおよそ 1 セッション。各項目の「終わり」を満たしたら commit し、HANDOFF を書き換える。
A は 2026-11-14 に終わった。**次は B0 → B1 → B3 → B2 の順**（A2 の結果で決めた。理由は HANDOFF）。

実録音の扱い: RWC-P の **P001〜P050 は見て決める側、P051〜P100 は決めるときに見ない側**。
変更のたびに 100 曲全部を測って README に載せるが、値を選ぶ・誤りを調べるのは前半だけで行う
（2026-11-14 の最初の測定では、100 曲の集計と、小節線を落とした曲の一覧を両方の半分について見た）。

### A. 実録音で測る（M1）: 完了

- **A0 測定の道具を repo に入れる。** いまは `scratch/`（commit の外）にある `run.py`・`sweep.py`・
  `doubt.py`・`barlines.py`・`keys.py` が測定の実体。`tools/measure.py` などに整理して commit する。
  終わり: README のコマンドだけで全セットの表が再現できる。
- **A1 正解つきの実録音を集める。** 候補は 2 系統。
  (a) ユーザーが持っている、コードの分かっている曲。
  (b) コードと拍の注釈がある公開データ。着手時にライセンスと中身を確かめる
  （候補として覚えているのは GuitarSet、AAM、Isophonics、McGill Billboard など。音源が配布されているか、
  注釈の形式、商用・再配布の条件はどれも未確認）。
  終わり: 20 曲以上を `truth.json` の形にする変換と、その一覧（出典・ライセンス）。音源は commit しない。
- **A2 実録音の現在地を測り、誤りを分類する。** テンポ・小節線・コードのどこで落ちるかを曲ごとに見る。
  終わり: README に実録音の表。誤りの上位 3 種類と、それぞれに効きそうな手を HANDOFF に書く。
  M2 の目安をここで書き直す。

### B. 聞き分けを実録音に近づける（M2）

- **B0 小節の長さと頭を実録音で直す。** A2 で分かった、小節線を落とす 3 つの形: (1) 遅い曲を倍のテンポ・
  半分の小節に読む（29 曲）、(2) 拍が裏に乗る・小節の頭が 1〜2 拍ずれる（12 曲）、(3) テンポを 1/2・3/4 に読む（11 曲）。
  手がかりの候補: ドラムの型（バスドラムとスネアの位置）、コードの変わり目の周期を 1 小節と決めつけない、
  テンポの事前分布（合成曲では捨てた案。実録音では分布が違うので測り直してよい）。
  終わり: 前半 50 曲で小節線 F 80% 以上、または効かなかった手の記録。合成曲の数字を落とさない。

- **B1 学習データを実物に寄せる。** 生成器の伴奏の型を増やす（ピアノのアルペジオ、ストローク、歌の代わりの旋律）、
  複数の SoundFont、音の加工（残響・イコライザ・圧縮・雑音・ピッチのずれ）。
  終わり: Lily# のサンプル 4 曲（`tools/sample_songs.py`）と実録音で、印の数が減りルートが上がる。
- **B2 モデルの入力を広げる。** いまは半拍 1 つのクロマ 24 個だけ。前後の半拍を見せる、クロマより細かい
  スペクトルを入れる、を順に試す。終わり: 七の和音の聞き分け（いま 74〜90%）が上がるか、上がらないと分かる。
- **B3 印の質。** 知らない音では全部のコードに印が付く。確信度の較正をやり直す。
  終わり: 実録音で「印 2〜3 割・誤りの 8 割を拾う」か、それが無理な理由。

### C. 譜面としての組み立て（M3）

- **C1 曲の頭。** 頭の無音、弱起、イントロ。いまは「音は 0 秒から、1 小節目の頭から」を前提にしている。
  生成器に `--pickup` と頭の無音を足して測る。
- **C2 繰り返しを見つける。** 同じ 8 小節が繰り返されたら `section` と `form` にまとめ、コード行を短くする。
  同じはずの小節同士で読みを照らし合わせれば、コードの誤りも減らせる。
- **C3 テンポの大きな変化。** リタルダンド、フェルマータ、途中で止まる曲。小節ごと 5% の揺れで崩れ始める（README）。
- **C4 2 小節コードと平行調。** 音だけでは決まらないと分かっている。ドラムの型など別の手がかりが
  実録音で使えるかを見る。使えなければ `--tempo` と印で人に任せる。

### D. 道具にする（M4）

- **D1 横に置くファイルの仕様を決める。** `.dettato.json` の項目を確定し、Lily# 側と突き合わせる。
- **D2 配る形を決める。** Python のまま配るか、モデルを ONNX にして .NET のコマンドにするか。
  速さ（いまは特徴量の計算が 1 曲数秒）、依存の重さ、Lily#・Calamo との揃え方で決める。**ユーザーの判断が要る。**
- **D3 mp3 などの入力、コマンドの体裁、エラーの言い方。**
- **D4 VS Code の Lily# 拡張から呼ぶ。** 録音を選ぶ → `.lys` が開く → 小節を選ぶと原音が鳴る。

### E. コードの先（M5）

旋律、ベース、ドラムの順。着手の前に、既存の手法でどこまで行くかを 1 セッションで測ってから決める。

## 4. セッションの進め方

### 始めるとき

1. この ROADMAP と HANDOFF を読む。
2. HANDOFF の「環境」どおりに動くことを 1 コマンドで確かめる（全セットの測定が前回の数字と一致する）。
3. HANDOFF の「次の一手」から始める。別のことを始めるなら、理由を先に言う。

### 終えるとき（義務）

1. 全セットを測り直し、README の表を合わせる。書き出した `.lys` を `lysc check` に通す。
2. commit する（push はしない）。
3. **HANDOFF を書き換える。** 追記ではなく書き換え。200 行を超えさせない。経緯は git の履歴に任せ、
   HANDOFF には現在地・次の一手・捨てた案・未決の判断だけを残す。
4. ユーザーへの報告は結論から。数字は前回 → 今回で示し、確かめていないことを分けて書く。
5. **次をどちらで進めるのが有利かを、必ず報告の最後に書く。** 形式は次のとおり。

   > **次の進め方: 同じセッションで続ける / 新しい会話で始める**
   > 理由: （1〜3 点）
   > 新しい会話で始める場合に最初に読むもの: （ファイル名）

   判断の目安:

   | 同じセッションで続ける方が有利 | 新しい会話で始める方が有利 |
   |---|---|
   | 次の一手が、いま頭にある細部（調査中の曲、試した値、まだ書いていない所見）を直接使う | 項目の「終わり」を満たして commit し、HANDOFF が最新になった |
   | 途中の実験や未 commit の変更が残っている | 次の一手が別の作業の流れ（A → B など）に移る |
   | 会話がまだ短く、要約（コンテキストの圧縮）が起きていない | 会話の要約がすでに起きた。細部は失われているので、続ける利点が小さい |
   | 原因の切り分けの途中で、仮説がまだ絞れていない | 長いログや捨てた仮説が会話に溜まり、次の判断を引きずりそう |

   迷ったら「新しい会話」を勧める。そのために HANDOFF を、読めば続きができる状態にしておく。
   「同じセッションで続ける」を勧めるときも HANDOFF は書き換える（会話は予告なく要約されるため）。

## 5. ユーザーに決めてもらうこと

- **実録音。** 測るのは RWC-P 100 曲で足りた。ユーザーが使いたい種類の曲（弾き語り、ライブ録音など）が
  RWC-P と違うなら、コードの分かっている曲を数曲もらえると、その種類での数字が出せる。
- **RWC を学習に使うか。** RWC は CC BY-NC 4.0。測るだけなら問題ないが、学習に使ったモデルを配るなら
  非営利の条件がモデルに及ぶかを決める必要がある。決まるまで学習には使わない（合成曲と、条件の緩いデータだけ）。
- **配る形（D2）。** Python のままか、.NET のコマンドか。
- **名前。** 「Dettato」の重複は Web 検索で見ただけ。Marketplace・GitHub・NuGet・商標は未確認。
- **リモート。** `https://github.com/yotsuda/Dettato.git` を作って push するのはユーザー。
